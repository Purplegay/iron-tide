# v0.27.18 · 对局调用统计日志

## 使用

重启源码版游戏后，新开或载入对局都会自动开始记录，不必手动按性能快照。目录：

`%APPDATA%/Godot/app_userdata/Iron Tide RTS/performance_calls/`

每次进入对局生成独立文件名，包含时间、进程、运行时戳与 match_id 前缀；同一存档重新进入也不会覆盖前次日志。

- `.log`：可直接阅读，每段列出调用次数前 20 名、估算累计耗时前 20 名。
- `.jsonl`：每行一条完整记录，包含全部 41 个登记入口中实际被调用的函数、源文件与函数名，适合发来分析。
- `.json`：结算、返回大厅或正常关闭游戏时自动导出的单份完整报告；发来分析优先选择这个文件。包含 `header`（对局身份与采样口径）、`windows`（全部窗口及退出尾段）、`summary`（本次进入对局的汇总）。游戏运行期间仍先写 `.jsonl`，不反复重写整份 JSON。

每 30 秒现实时间追加一段，不受游戏倍速影响。暂停时仍可记录界面活动，但暂停及恢复首帧不计入有效帧百分位；记录暂停时长和窗口焦点状态。正常退出、返回大厅及结算时补写不足 30 秒的尾段。进程崩溃或被强制关闭时，当前未刷新的尾段可能丢失，已刷新的记录保留。

JSON 汇总包含加权平均帧耗时、最大帧、全部登记函数的累计调用次数与采样耗时排名、采样时刻的单位/建筑峰值、寻路统计、结束原因和实际推进速度。`session_sim_s` 累加本次进入后的有效游戏进程 delta（含倍速，排除暂停/禁用），`effective_speed = session_sim_s / session_wall_s`，墙钟分母包含暂停；不继承存档之前的游戏时长。新日志将所有窗口的稀疏帧直方图合并为整局 P95/P99，同时保留窗口值；历史 JSONL 没有直方图时只提供窗口值，不把窗口百分位平均后冒充整局百分位。统计是入口汇总，不是逐单位、逐次攻击的事件回放。

导出在现有后台写入线程中逐行读取 JSONL，避免把整局日志放进内存；先写临时文件，成功后才发布 `.json`。`export_complete` 表示日志导出完整，`battle_ended` 才表示对局结束，两者独立。读档重新进入同一场战斗也会生成新的会话文件。异常终止可能没有最终 `.json`，此时保留的 `.jsonl` 仍可用于分析。

原来的手动性能快照继续可用，新增 `call_log` 字段指向当前日志。未打包，旧试玩包不会自动更新。

## 记录范围与开销控制

主要入口包括单位物理更新、交战、索敌、移动、技能检查、局部避让、运输、维修、AI 决策／选址、A*／窄道寻路、迷雾、HUD、小地图、单位／建筑／弹体／RA2 特效绘制。登记清单以 `battle_call_counters.gd` 的 POINTS 为准，并写在日志首行。

调用次数是这些入口的完整计数；高频函数耗时采用平均每 4～64 次一次的抖动抽样，低频重操作逐次计时。使用独立整数采样序列，不消耗游戏随机数。估算累计耗时 = 样本均值 × 调用次数；会记录样本数量和样本最大值。父函数包含子函数时间，不能相加，也不代表覆盖全部脚本函数或 GPU 时间；样本最大值不等于该函数所有调用的真实最大值。

帧耗时覆盖完整 30 秒窗口，用固定大小的 1ms 直方图统计 P50/P95/P99，向上取整；超过 5000ms 的百分位只显示下限，同时记录溢出数量和真实最大帧。每段关联活单位／建筑数量与类型、弹体、特效、寻路次数、物理频率、刷新档位、绘制调用及内存。

主线程只计数、抽样计时并整理每段小摘要，不逐次写文件；JSON 序列化、排序和磁盘追加在后台线程执行。最多保留 4 个待写摘要，磁盘过慢时延长统计窗口、保留计数。写入失败会输出警告并停止本场统计，不无限重试。退出时等待已有写入完成。

日志是每 30 秒的摘要，不保存逐调用事件；不会自动删除历史对局。需要性能基线时，可仅对测试进程设置 `IRON_TIDE_CALL_LOG=0` 关闭采集。
