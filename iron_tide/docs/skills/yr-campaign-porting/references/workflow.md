# 执行流程与双表模板

## 接入：先闭环一个样本，再扩同语义

1. 填任务卡：`地图 ID / 原图路径与 SHA / 当前阶段 / 用户本轮要的范围 / 真实菜单路径 / 正式装配与驱动入口 / 测试场景 / 最新交接`。开工先核对工作树，防止重复移植已接的行。用 `rg --files` 找同关导出器、数据和测试，优先沿用已有格式，工具命令从该关交接复跑。
2. 先提取两张表，记录原始值，不根据触发器名字猜动作。只有结构相同才分成一批：例如标签发现、定时增援、建筑失守、工厂编制。对被禁用或未确认可达的条目保留原标志。
3. 选一条代表性零售 ID，贯穿「导出 → 关卡表 → 正式战场条件 → 动作适配 → 玩家可见结果 → 否定例」。从真实菜单验证，确保不是仅在测试里手工执行。再复用同一入口成组扩展，避免每条单独手写流程。若地图或单位尚未接好，先交一条可用的正式链，并标明这是阶段交付。
4. 涉及新图时并行推进地图和任务资料，不等视觉完成才查脚本。地形、覆层、建筑、桥坡、CG、美术高光按 [完整检查表](full-checklist.md) 的专项门槛，不能只搬画面或只跑脚本。

### 可复制的台账列

```text
任务：ID | 原始事件/动作/标签 | 房/难度/启停 | 条件/时间起点/单位 | 对象/后继/取消 | 正式入口 | 玩家结果 | 状态及证据
地图 AI：AI ID | 原始条件及启用记录 | 房/难度/权重 | 条件/资金/科技/工厂 | TeamType/TaskForce/ScriptType/航点 | 选中/扣费/出厂/接令/行动 | 证据及限制
```

每个状态单独记：已取证／已导入／已接线／已实测；不适用、不可达、暂未获取证据、已重现失败分别保留。把生产设施实际可达性与“设施就绪后的出兵能力”分开。若多条条件共用同一 TeamType，允许复用测试夹具，但不把条件的独立验证直接去重；仅统计脚本编组时才按实际稳定编组 ID 去重。

### AI 规则已启用，怎样确认战役会选队

从规则 ID 同时展开主、副 TeamType，查 TaskForce、Script 字段和具体 ScriptType。另列本图触发器直接创建的队伍，记录定义来自 MAP 还是继承的 AIMD。分别解码地图 `[Actions]` 和队伍 `[ScriptTypes]` 的指令；遇到设置变量的脚本，继续查监听该变量的事件及后继动作。声称某类指令在整份来源中缺席时，扫描该来源全部注册脚本，并记下范围和命中数。

按房屋和战役阶段依次核对生产、自动编队、AI 条件评估各自的启动来源，再查该规则是否获选、下单、出厂。地图的逐 ID 启用值只回答规则层的问题。若启动证据止于某一步，在该 ID 的台账写明查过的路径和缺口；人为补厂、给钱或直接调用选队所得的结果注明夹具条件。能否在原关自然发生，留给对应的启动路径或实测判定。

### 依赖绑定对象的动作怎样结项

先查动作语义，确认目标来自绑定对象、参数指定对象还是整房。对使用绑定对象的动作，从目标触发器沿 Triggers 的链接字段反查**全部前驱**，对每个可达触发器查指向它的 Tag。复用项目 `tools/retail_trigger_bindings.mjs`，在 Tags 定义之外按字段扫描引用，包括预置对象、CellTags、小队和动作；有命中时逐项解释它怎样提供对象。另查初始启停、启用和强制动作的来源，回答何时执行。

台账按 ID 保存动作、链接、标签、引用位置及启停来源。确认动作必须使用绑定对象且所有来源均查清、没有目标时，标为“原图无绑定对象”，单列结项数。遇到语义未解或引用来源尚未查清，保留待核验。一个触发器含多个动作时，逐个判断效果后再给整条定状态。

## 验收：按玩家路径和边界取证

- 正式菜单出击，查第一项玩家操作和目标，再到结算与返回。覆盖胜利、全灭、一个任务专属失败；失厂、替代增援、提前达成、未占领等分支按本关脚本选择，不直接修改胜负标记制造通过。
- 一个开场、中途、后段至少各选最有价值的断点；高风险动作额外在“进行中”写档，独立进程冷读。见 [无头取证](headless-evidence.md)。结算、奖励、任务动作都检查不漏不重。
- 分开记录夹具、自然命令和自然整关的覆盖。CG 遇到独立续音，要验证实际时钟、留帧、字幕及交控；收藏回看另验。视觉及听感只有授权的有头实测才能签字。

