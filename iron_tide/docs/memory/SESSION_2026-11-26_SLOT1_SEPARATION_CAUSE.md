# 六家对战避让热点成因

本轮逐项分析 `Unit.apply_separation()`。`CombatTree2` 存档 1、3 倍速的最慢七帧中，该入口全局平均 1222 次，包含子调用 16.84 ms/慢帧。12.84 ms 是扣除已插桩子调用后的余量，其中仍包含未单独计时的 `LocalTraffic.apply`。该计数覆盖所有入口。`_move_toward` 和另一处移动调用都能进入避让，父子边数据为空，无法精确归到 `_process_combat`。

`local_traffic.gd:167` 先按时间或位移刷新候选，再计算推力、借道和对向车辆减速。大场使用格索引收集矩形内的单位，再按对象有效性、碰撞层和圆形边界筛选。候选刷新半径包含前视和余量。缓存的对象名单还供 `stalled_blockers` 等读取。位置、阵营、碰撞域和让行状态在消费时读取。

当前战场为 15 Hz。3 倍速采样每个物理步传入 0.2 秒游戏时间，`query_left` 每次避让扣减这个值，刷新只设为 0.1 秒。因此已经建立的候选名单在下一次避让调用前也会耗尽时间预算。步数上升会按步重复该工作。直接延长时间会改变邻居进入名单的时机，仍要核对 24 像素位移条件、候选移动、传送、桥层与脱困消费者。

旧存档 3 的固定 450 物理步诊断中，刷新候选 0.949 ms/步，逐候选避让 0.324 ms/步，遍历 110422 项，平均每次避让循环约 4.14 项。两者约 3:1，供定位线索。证据 `.validation/motion-chunks-20261124/detail/fixeda3/methods.json`。这些分项来自旧存档 3，当时外部引擎审计标记为真。当前存档 1 只确认入口总耗时及源码上的定时失效，尚缺同场的候选收集、半径筛选与第二轮遍历耗时。检查时有其他 Godot 进程，本轮未新增正式采样或修改玩法源码。
